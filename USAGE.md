# licenseal — Usage & reference

Full CLI reference, resolution behavior, and per-ecosystem detail. For the overview, install, and the "why," see the [README](README.md). For the security/egress model see [SECURITY.md](SECURITY.md); for the JSON schema see [JSON_OUTPUT.md](JSON_OUTPUT.md).

## Commands

```bash
licenseal check                 # scan the current project and gate on the result
licenseal init-review-file      # scaffold a licenseal.review.toml for flagged deps
licenseal install-skill         # install the Claude Code review skill into the project
licenseal --version             # print the version and exit
```

### `licenseal check` options

| Flag | Default | Notes |
|---|---|---|
| `--path PATH`, `-p PATH` | `.` | Directory to scan |
| `--format FMT`, `-f FMT` | `table` | `table`, `json`, or `markdown` |
| `--output FILE`, `-o FILE` | — | Write report to FILE instead of stdout |
| `--dev / --no-dev` | `--no-dev` | Include dev dependencies |
| `--strict / --no-strict` | `--strict` | Fail closed on warnings + unknowns + analysis gaps (violations always fail) |
| `--require-lockfile / --no-require-lockfile` | `--require-lockfile` | Whether a manifest whose dependencies no lockfile covers is an analysis gap. `--no-require-lockfile` accepts the registry estimate and reports it without failing. No effect with `--no-transitive`. |
| `--transitive / --no-transitive` | `--transitive` | Full-tree scan vs direct deps only |
| `--max-depth N` | `50` | Cap the depth of a registry walk (see [Per-ecosystem resolution detail](#per-ecosystem-resolution-detail)), 1 to 100. A usage error with `--no-transitive` |
| `--max-workers N` | `16` | Concurrent registry requests, 1 to 32 |
| `--exclude-dirs PATH[,PATH...]` | — | Skip subdirectories during discovery. Comma-separated and/or repeated flag (relative to `--path` or absolute). Subdirectories that contain their own `.git` are skipped automatically. |

### `licenseal init-review-file` options

| Flag | Default | Notes |
|---|---|---|
| `--path PATH`, `-p PATH` | `.` | Project directory, where `licenseal.review.toml` is written. Without `--from-report` it is scanned as `check` scans it by default: lockfile-first, transitive dependencies included |
| `--dev / --no-dev` | `--no-dev` | Include dev dependencies |
| `--from-report PATH` | — | Read flagged deps from a saved JSON report (offline, no registry round-trip). A usage error together with `--dev` / `--no-dev`, `--max-workers`, or `--exclude-dirs`, which only apply to a scan |
| `--merge` | — | Add new flagged entries to an existing review file (preserves existing entries). Without it the command fails rather than overwrite an existing file |
| `--max-workers N` | `16` | Concurrent registry requests, 1 to 32 |
| `--exclude-dirs PATH[,PATH...]` | — | Skip subdirectories during discovery (same semantics as `check`) |

## Common usage

```bash
licenseal check                              # full-tree scan (default; lockfile-first, registry fallback)
licenseal check --no-transitive              # direct deps only (use when publishing a library)
licenseal check --dev                        # also include dev dependencies
licenseal check --no-strict                  # advisory mode — don't fail on warnings/unknowns/gaps (violations still fail)
licenseal check --no-require-lockfile        # no lockfile committed — accept versions and transitives estimated from the registry
licenseal check -f json -o report.json       # machine-readable output for CI tooling
licenseal check -f markdown -o LICENSES.md   # PR-comment-friendly Markdown audit
licenseal check --exclude-dirs third_party,scratch  # skip subtrees not already in the default skip set
```

## Project license

Every verdict compares a dependency's license with the project's own. licenseal reads the project license from the manifests in the scanned directory itself (the `--path` root) and never from a subdirectory: a nested package's license is that package's.

- The manifests are consulted in this order, and the first one that declares a license decides: `pyproject.toml`, `setup.cfg`, `setup.py`, `package.json`, `Cargo.toml` (`[package]`, then `[workspace.package]`), `pom.xml`, `.csproj` / `.fsproj` / `.vbproj`, `Directory.Build.props`, `composer.json`, `*.gemspec`, `mix.exs`, `DESCRIPTION`.
- A .NET solution whose projects live in subdirectories declares its license in the `Directory.Build.props` of the solution root, the file MSBuild imports into every project beneath it. licenseal reads `PackageLicenseExpression` from it, or `PackageLicenseUrl` when there is no expression (the URL of a canonical license page), exactly as from a project file. Only the properties written in that file's own `<PropertyGroup>` elements are read: a `Condition` is not evaluated (the property counts either way), a file it brings in with `<Import>` is not read for this, and neither is a property inside a `<Choose>` branch, `Directory.Build.targets`, or a `Directory.Build.props` in a subdirectory. A project file in the scanned directory is consulted before it.
- `check` and `init-review-file` print one stderr line with the value and the file it came from: `Project license: MIT (from pyproject.toml).`
- When no manifest in the scanned directory declares a license, the project is checked as `Proprietary` (a closed-source project can use permissive dependencies but not copyleft ones), and the line says so: `Project license: Proprietary (assumed: no manifest in the scanned directory declares a license). Scanning a subproject with --path uses that subproject's license.` To check one package of a monorepo against its own license, scan it with `--path`.
- A declared value that is not a recognised license (`"license": "-"`, a sentence, a name with no SPDX mapping) is not used. A `Warning:` names the file and the value, and the project is checked as `Proprietary`.
- In `setup.cfg`, `[metadata]` `license` is read first and the `classifiers` after it, with `%` interpolation, as setuptools reads them. A value that cannot be interpolated (a stray `%`, as in `license = 100% free`, or a `%(name)s` reference to an option that is not there) declares no license: the file is passed over like a manifest with no license field, without a warning of its own. Write a literal percent sign as `%%`.
- When manifests in the scanned directory declare different licenses, the first in the order above decides and a `Warning:` names each file and its value.
- The JSON report carries the file as `project_license_source` (`""` when `Proprietary` is assumed). The table and Markdown reports show it beside the project license.

## Output & the CI gate

`licenseal check` exits non-zero when there are violations, warnings, unresolved licenses, or analysis gaps — that's the CI gate.

- An **analysis gap** is a dependency manifest or lockfile that couldn't be read (permission / I/O error, or a file over 128 MiB, which is skipped), decoded (a UTF-16 or UTF-32 byte-order mark on bytes that are not valid in that encoding, a TOML file that is not valid UTF-8, or a `pom.xml` whose prolog names a multi-byte or unknown encoding), or parsed (malformed XML / JSON / TOML / YAML / INI, a JSON / TOML / YAML document nested too deeply to parse, or a `setup.py` that is not valid Python 3), a directory that couldn't be traversed, a manifest that points at another file through a path that is not followed (an MSBuild `<Import>` or `go.work` `use` value that is not a relative path; a requirements `-r` include that is a URL, is not a relative path, is not a file, or leaves the scanned directory), a file that parses but holds a value of a type its format does not allow, a lockfile that cannot be used, a `composer.json` that takes packages from repositories it does not name them for (all three described below), or a `go.mod` below `go 1.17` whose requirements have no `go.sum` row, so that what they depend on cannot be listed (see the Go notes under [Per-ecosystem resolution detail](#per-ecosystem-resolution-detail)) — each is surfaced as a `Warning:` on stderr so a dropped dependency is never silent. Gaps fail strict mode like an unknown; a non-UTF-8 text, JSON, or YAML file recovered via latin-1 fallback warns but does not fail, with or without a UTF-8 byte-order mark, and neither does a lockfile in a version licenseal was not written for. The report itself records them too, on stdout and in an `-o` file: the table and Markdown formats add the gap count to the summary line and an **Analysis gaps** section listing each file with its reason (both appear only when there is a gap), and JSON carries `summary.gaps` and `diagnostics`. In the table and Markdown formats a file outside the scanned directory is named by its file name only, so a saved report does not depend on where the project was checked out.
- A manifest without a lockfile is an analysis gap as well. When a manifest declares a direct dependency that no lockfile covers (there is no lockfile for its ecosystem, the lockfile does not list the dependency, or it lists it only at versions the declaration does not admit, as when a manifest has moved ahead of its lockfile), that dependency and everything under it are resolved through the registry, and the result is an estimate of what the project installs. The manifest gets one diagnostic, `declares dependencies that no lockfile covers; their versions and transitive dependencies are estimated from the registry`, and stderr carries one line for all such manifests, after the per-file warnings, naming the two ways out: commit a lockfile, or pass `--no-require-lockfile`. With `--require-lockfile` (the default) the diagnostic is a gap: counted in `summary.gaps`, listed under **Analysis gaps**, failing strict mode. With `--no-require-lockfile` it is still reported, with severity `estimate`: on stderr, in JSON `diagnostics`, and in the table and Markdown formats as an `N estimated manifest(s)` count on the summary line and an **Estimates** section listing each file; it is not counted in `summary.gaps` and does not fail. This covers Python, npm, Rust, PHP, Ruby, Hex (`mix.exs`, `rebar.config`), and R manifests, Gradle build files, and .NET project files, `Directory.Build` and `Directory.Packages.props` files, and `paket.dependencies`. It does not cover a manifest of a tool with no lockfile format (Maven `pom.xml`, NuGet `packages.config`, an erlang.mk `Makefile`), whose rows are marked as estimates, where licenseal picked the version, without a diagnostic; Go; an [off-registry dependency](#off-registry-dependencies), which is not resolved through a registry and is never an estimate; a manifest whose only uncovered dependencies are dev dependencies in a scan without `--dev`; or `--no-transitive`, where no lockfile supplies versions and no transitive graph is reported.
- A dependency list that a registry did not give is an analysis gap. A registry walk (see [Transitive scanning](#transitive-scanning)) asks the registry for the dependencies of each package it reaches. When they cannot be determined, the manifest that declares the direct dependency the package was reached from gets `the dependencies of <name> <version> could not be read from the registry; its transitive dependencies may be missing`: the package is still reported and its license resolved, and what it requires is what may be missing. That covers a request that still fails after its retries; a Maven version deps.dev does not have, or a deps.dev graph returned with an `error`; a response that is not shaped as the registry documents it; a PyPI `requires_dist` entry that cannot be parsed; a NuGet dependency with no version or with one that resolves to no published version; and a `.nuspec` walk that reaches its limit of 32 levels below a direct dependency. A package is recorded once per manifest, however many of that manifest's direct dependencies reach it. It is a gap with or without `--no-require-lockfile`, and on a Maven `pom.xml` as well. A package that declares no dependencies records nothing. Not recorded: a Go module whose `go.mod` the module proxy does not serve (every module is already a row from `go.sum`; only its attribution is lost), an R package missing from the CRAN index (its license comes from the same record, so it is itself `UNKNOWN`), a package no version could be resolved for (reported as `UNKNOWN`), other than the NuGet dependency of a `.nuspec` named above, and a walk stopped by `--max-depth`, which prints a warning.
- A value of the wrong type is a gap on the file that holds it, reported as `<what> has an unexpected type; ignored`: a string or list where a dependency section must be a table (`"dependencies": []` in `package.json`, `dependencies = "flask"` in `pyproject.toml`), a version or constraint that is not a string, a lockfile entry that is not the shape the lockfile format defines. This applies to `package.json`, `pyproject.toml`, `Pipfile`, `composer.json`, `uv.lock`, `poetry.lock`, `Pipfile.lock`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` (Berry), `bun.lock`, `composer.lock`, and `renv.lock`. The value is read as if it were absent and the rest of the file is still read: a section declares nothing, a dependency whose constraint cannot be read is kept without one, a lockfile entry whose version cannot be read pins nothing. `null`, and an empty value of the expected type, declare nothing and are not gaps; in `composer.json` and `composer.lock` an empty list where a map is expected is also an empty map, since that is how PHP writes one. The project's own `name` and `license` fields are not dependency data: one of the wrong type reads as absent without a gap.
- A lockfile that cannot be used is a gap and is skipped, in three cases: it declares a format version licenseal is known not to read (`declares a lockfile version that is not supported; skipped`), which is `pnpm-lock.yaml` `lockfileVersion` below 6, where packages are keyed as `/name/version`; it has entries and none is in a form licenseal reads (`holds no entry in a form that can be read; skipped`); or it is a line-oriented lockfile with merge-conflict markers (`contains merge-conflict markers; skipped`). The direct dependencies are then resolved through the registry as if the lockfile were absent, so the reported versions can differ from the locked ones. A lockfile with no entries, and one whose packages are all filtered out afterwards (dev-only packages without `--dev`, the project's own packages), is not a gap.
- A `composer.json` is a gap when it requires a Packagist package, declares a repository whose packages it does not name, and no `composer.lock` is read for it (`declares repositories (<types>) without naming their packages, and no composer.lock was read for it: those packages cannot be told from registry packages and may have been resolved from Packagist`). Those repositories are the version-control types (`vcs`, `git`, `github`, `gitlab`, `bitbucket`, `git-bitbucket`, `forgejo`, `hg`, `svn`, `fossil`, `perforce`), `artifact`, and a `path` repository the scan does not read. Composer learns what such a repository provides by reading it; licenseal does not, so a requirement the repository satisfies is looked up on Packagist under its name, and the report cannot say which rows those are. The `composer.lock` beside that `composer.json` closes the gap. `--no-transitive` takes no dependency rows from a lockfile, so there the gap is reported whether or not a `composer.lock` exists. A `package` repository names its packages, a `path` repository the scan reads has its packages scanned, and a `composer` repository is another registry: none of them is a gap.
- A lockfile in a version licenseal was not written for is still read. The parsers were written for `package-lock.json` `lockfileVersion` 1, 2, 3; `pnpm-lock.yaml` `lockfileVersion` 6.x and 9.x; `yarn.lock` v1 and Berry `__metadata.version` 4 to 10; `bun.lock` `lockfileVersion` 0 and 1; `uv.lock` `version` 1; `poetry.lock` `lock-version` 1.x and 2.x; `Pipfile.lock` `pipfile-spec` 6; `packrat.lock` `PackratFormat` 1.x. A lockfile that declares a newer version is read on a best-effort basis and reported with a warning that is not a gap and does not fail strict mode (`declares a lockfile version newer than the parser knows; read on a best-effort basis`). Any other value that is not on the list, apart from pnpm below 6, is read the same way (`declares a lockfile version the parser does not know; read on a best-effort basis`). If nothing in such a lockfile can be read, that is the gap described above. A lockfile that declares no version is read without a warning.
- The lockfile checks in the two points above cover the lockfiles just listed and `composer.lock`, `Gemfile.lock`, `mix.lock`, `gradle.lockfile`, and `renv.lock`. They do not cover `Cargo.lock`, `go.sum`, `packages.lock.json`, `project.assets.json`, `paket.lock`, or `rebar.lock`.
- Text, JSON, YAML, and TOML manifests and lockfiles written as UTF-16 or UTF-32 with a byte-order mark, or as UTF-8 with one (what a Windows shell redirect produces), are read in that encoding; this includes `pyproject.toml` and the other TOML files. TOML requires UTF-8, so a TOML manifest or lockfile (`pyproject.toml`, `Pipfile`, `Cargo.toml`, `uv.lock`, `poetry.lock`, `Cargo.lock`) with no UTF-16 or UTF-32 byte-order mark that is not valid UTF-8 gets no latin-1 fallback: it is an analysis gap (`is not valid UTF-8, which TOML requires; skipped`), wherever the invalid byte is. XML manifests are decoded by the XML parser from their own prolog or byte-order mark.
- `--no-strict` demotes warnings / unknowns / gaps to advisory. **Violations always fail** — they're definite legal incompatibilities and the flag won't silence them.
- If **every** registry lookup fails and not one dependency resolves (no network, blocked egress, registry-wide outage), `check` aborts with an error and a non-zero exit rather than reporting an all-UNKNOWN scan; this is not demotable by `--no-strict`.

The `-o / --output FILE` flag writes the rendered report to a file (UTF-8, no ANSI escapes for table format). The file is written **before** the strict-mode gate runs, so CI can publish the artifact even when `check` exits non-zero. Since the report itself doesn't reach the terminal, a failing check then also prints the summary and the findings that failed it (plus the number of analysis gaps) to stderr, so CI logs and pre-commit output show why without opening the file. JSON is the stable machine-readable format — see [JSON_OUTPUT.md](JSON_OUTPUT.md) for the schema.

The table and Markdown formats escape the strings that come from registries and scanned files (package names, versions, license strings, manifest paths, review notes) for display. Control characters are shown as `\xNN`; line breaks and tabs become a space. A lone surrogate (an unpaired `\uD800`–`\uDFFF` escape in a JSON manifest or registry response), which no encoding can write, is shown as `\uNNNN`. Markdown reports backslash-escape `\`, `` ` ``, `[`, `]`, `<`, `>`, and `|`, so a string cannot add a link, an image, HTML, or a table column. Link URLs carry the name percent-encoded. JSON reports the original strings.

The table is laid out for where it goes, and never drops a column:

- **Not a terminal** (a pipe, a CI log) **or an `-o` file**: the table is written at its full width, one line per dependency, with no cell wrapped or cut short. Lines can be longer than 80 columns.
- **A terminal narrower than the table**: package names, manifest paths, and license expressions fold over several lines; the Ecosystem, Group, Risk, and Status columns stay whole. Below 80 columns those fold too.

When stdout's encoding cannot represent the report's glyphs (a redirected stdout under a legacy Windows code page such as cp1252), the table and Markdown formats print `OK`, `!`, and `X` for ✓, ⚠, and ✗, and `+-` for the tree branch; any other character the encoding lacks is printed as `?`. An `-o` file is always UTF-8 and keeps the original glyphs, and JSON is plain ASCII.

## Transitive scanning

Transitive is the default. `--no-transitive` audits only the manifests you declared directly: it takes no dependency rows from a lockfile, requests no dependency graph, and reports no row beyond the direct dependencies. A `pom.xml` dependency whose version is left to the parent chain (a parent's `<dependencyManagement>`, a BOM it imports, a `${property}` a parent defines) is reported at the version the chain supplies in both modes; for that, `--no-transitive` reads the parent and BOM POMs, in the tree or from the registry. The walk uses a **lockfile-first** strategy:

1. If a lockfile is present, it is the source of truth: `uv.lock`, `poetry.lock`, or `Pipfile.lock` (Python); `package-lock.json` (v1/v2/v3), `pnpm-lock.yaml`, `yarn.lock`, or `bun.lock` (npm); `Cargo.lock` (Rust); `go.sum` (Go); `gradle.lockfile` (Gradle); `packages.lock.json`, `project.assets.json`, or `paket.lock` (.NET); `composer.lock` (PHP); `Gemfile.lock` (Ruby); `mix.lock` / `rebar.lock` (Hex); `renv.lock` / `packrat.lock` (R). Lockfiles encode the actually-resolved graph, so this path is precise and offline-fast. A lockfile in a newer version than licenseal was written for is still read, with a warning; one in a version known not to be readable is skipped and reported as an analysis gap (both are listed under [Output & the CI gate](#output--the-ci-gate)). `composer.lock` is uniquely informative: each entry embeds a structured SPDX `license` field, so the Packagist resolver answers most queries without any HTTP fetch.
   A lockfile covers a direct dependency only when it holds that package at a version the declaration admits: `shared>=2` is covered by a locked `2.4.0`, not by a locked `1.0.0`. The declaration is read in its ecosystem's own grammar (see [Resolution semantics](#resolution-semantics)); a bare NuGet, Maven, or Gradle version is a minimum. A declaration that cannot be compared with the locked version counts as covered: one with no constraint, one that is not a version range (a dist-tag, a branch, an unresolved property), and any range when the locked version is a prerelease the range does not name, since settings outside the manifest decide whether a resolver takes one. A declaration that no lockfile covers is resolved through the registry (step 2), and its manifest is recorded as lacking a lockfile. That is the case for a sub-project that pins another version than a lockfile elsewhere in the tree holds, for a project without a lockfile beside a sub-project that has one, and for a manifest whose own lockfile is out of date. A lockfile row is reported as a direct dependency, with a manifest as its `source`, only at a version that manifest's declaration admits; another locked version of a declared package (the copy an npm or Cargo lockfile nests under some other package, or the stale entry of an out-of-date lockfile) is a transitive with an empty `source` and an empty `direct_ancestors`. `gradle.lockfile` and `paket.lock` do not tell direct from transitive: their rows stay as the file lists them, and only take a manifest as `source` at a version its declaration admits.
   A lockfile is read wherever it is found in the scanned tree, with two exceptions for npm: a lockfile under a directory named `test` or `tests` is not read (the `package.json` beside it still is), and when one directory holds several npm lockfiles only the first of `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` is read. A lockfile is read even when no manifest yields a direct dependency for its ecosystem: a lockfile with no manifest beside it, a Gradle build that declares everything through a version catalog, a `PackageReference` kept in a props file that a project imports with its own `<Import>`. When none of a lockfile's packages is a direct dependency found in the manifests, none of them is dropped. A format that records its own dev/prod split (`Pipfile.lock` sections, `composer.lock` `packages-dev`, `gradle.lockfile` test classpaths, `paket.lock` groups) keeps it; in every other format licenseal cannot tell which packages are dev-only or which direct dependency pulls each one in, so all of them are reported as `prod`, generally as transitives with an empty `direct_ancestors`. Consequently a sample or test-data lockfile outside the [auto-skipped directories](#discovery-auto-skipped-directories) adds its packages to the report; exclude its directory with `--exclude-dirs`.
2. When no lockfile exists for an ecosystem, licenseal falls back to recursive registry walks: each dep's per-version metadata is fetched and walked breadth-first in parallel (per `--max-workers`). Multiple resolved versions of the same package coexist in the output — a graph can legitimately contain `lodash@4.x` and `lodash@3.x` via different paths, each license-resolved independently because a package can ship under different licenses across majors. So do the versions that different manifests of one tree ask for: when two manifests declare one package with different version constraints (`shared==1.0` in one service, `shared==2.0` in another; two project files referencing different versions of a NuGet package; two modules of a Maven build), each declaration is resolved and walked on its own and reported with its own manifest as `source`. Two declarations with the same constraint are one dependency, with the extras of both, and production when either is; two that resolve to the same version are one row, and so are two that resolve to no version (a report has one row per package, resolved version, and origin). The same walk resolves a direct dependency that a lockfile is present for but does not cover. What a registry walk reports is an estimate: the versions are the ones the registries publish at scan time, not the ones the project installs. Every row it adds is marked as estimated (see [Resolution semantics](#resolution-semantics)), and each manifest it starts from is recorded as lacking a lockfile, which is an analysis gap unless `--no-require-lockfile` is passed (see [Output & the CI gate](#output--the-ci-gate)).

The report nests transitives directly beneath the depth-0 dependency that pulls them in, so a flagged transitive traces back to the direct dep you'd remove to drop it. Direct deps are listed alphabetically; under each, transitives appear in their own alphabetical run with a tree-style indent. Transitives shared across multiple direct deps are listed once under the alphabetically-first ancestor with an `(also: X, Y)` annotation; the full list is always in JSON under `direct_ancestors` (plus `depth` and `is_transitive`). Every dependency is exactly one row, so the table and Markdown reports have as many rows as JSON's `summary.total`: an ancestor is matched within the transitive's own ecosystem, and when several direct rows share an ecosystem and name (two locked versions of one package) their transitives are listed under the one with the first version. Group is attributed by reachability: a transitive reached from a `prod` direct dep is `prod`, otherwise `dev` if reached from a dev dep, otherwise dropped — so `--no-dev` reports cleanly omit dev-only chains. (A lockfile that contains none of the direct deps is the exception described above: nothing in it is dropped.) Production wins: a dependency declared as dev that a `prod` dependency also pulls in is reported as `prod`, and a package that one lockfile reaches only from dev dependencies and another reaches from production is `prod`. `--dev` adds rows; it never changes a `prod` row to `dev`. In the registry walks (step 2), for Maven, and in the NuGet `.nuspec` walk, reachability is followed per resolved version: when a dev dependency pulls in another version of a package that production also uses, that version is `dev`, and each version's `direct_ancestors` lists the direct dependencies that pull in that version. The `prod` rows of such a `--dev` scan are the rows of the `--no-dev` scan.

### Per-ecosystem resolution detail

- **Python**: PEP 508 environment markers are intentionally ignored (treated as always-true). License obligations don't depend on `python_version` or `sys_platform`, so missing a marker-gated copyleft would be a compliance gap. Extras are followed: with a `uv.lock`, packages installed through an extra (`django[argon2]` → `argon2-cffi`) come from the lockfile's `[package.optional-dependencies]` edges for every extra requested in the lock. In `requirements*.txt`, comments are stripped by pip's rule (`#` at the start of a line or after whitespace). A `-r <file>` / `--requirement <file>` line is followed: the path is taken from the directory of the file that contains the line, the included file can have any name, and a cycle of includes ends (each file is read once per starting file). The included requirements take the dev/prod classification of the `requirements*.txt` / `*-requirements.txt` file the chain of includes starts from, not of the included file's own name; a requirement reached from both a production and a dev file is production. Each is reported with the file that declares it as its source. An include is not followed, and is an analysis gap on the file that names it, when its path is a URL or is rooted, drive-qualified, UNC, or a device path (none of which is fetched or opened), when it is not a file, or when it resolves outside the scanned directory, through `..` or through a link. `-c` / `--constraint` files are never read: a constraints file adds no requirement, and its pins are not applied to the requirements either. A URL or VCS requirement (`name @ <url>`, or a bare `https://…` / `git+https://…` line, with or without `-e`) and a local wheel, archive, or directory path are [off-registry dependencies](#off-registry-dependencies). One written without a name is named after its `#egg=` fragment, otherwise the distribution name in a wheel or sdist file name, otherwise the last path segment, or the location as written when that leaves no letter or digit (`..`, `wheels/*.whl`). A `--hash=` beside a URL is its recorded hash. A relative path is taken from the directory of the file that names it; a path the scan reads, `-e .` included, is the project's own code and is not reported, and a wheel or an archive is a row wherever it lies. The other option lines (`--index-url`, …) are skipped. A requirements file under another name that nothing includes (`requirements/base.txt` on its own) is not scanned. In `pyproject.toml`, `setup.cfg`, and `setup.py`, a PEP 508 direct reference (`name @ <url>`) is an off-registry dependency. So are a Poetry dependency table with `git` / `url` / `path`, a `[tool.uv.sources]` entry with `git` / `url` / `path` (applied to the requirements of the same file and, from a uv workspace root, to those of its members, whose own entries take precedence; a member is a project below the root whose directory matches a `[tool.uv.workspace]` `members` glob and no `exclude` glob, and any other project below the root takes nothing from the root's table), and a `Pipfile` entry with `git` / `hg` / `svn` / `bzr` / `path` / `file`. The origin of a repository source is the repository plus `rev`, `ref`, `tag`, or `branch`, in that order of preference. A dependency that lists one table per environment is off-registry when any of the tables names such a source. `workspace = true`, and a path the scan reads, are the project's own code. A Poetry `source`, a uv `index`, and `--index-url` / `--extra-index-url` name an alternate index: the requirement stays a registry one and is looked up on PyPI. In lockfiles, the off-registry entries are a `uv.lock` `source` of `git` (origin: the repository plus the locked commit), `url` (the URL plus the artifact's hash), or `path` / `directory` / `editable` the scan does not read; a `poetry.lock` `[package.source]` of type `git` (the repository plus `resolved_reference`), `url` (the URL plus the file's hash), or `directory` / `file` at a path the scan does not read; and a `Pipfile.lock` entry with `git` (plus `ref`), or with `path` / `file` at a path the scan does not read. `registry` and `legacy` sources are registry packages. The registry packages that only a path package of the project needs are reported through that package's own manifest. A dependency every manifest declares off-registry keeps that origin when a lockfile lists its name as a registry package. When PyPI's JSON for the selected release carries no usable license, that release's own wheel metadata (its PEP 658 sidecar) is read next; the license of the project's latest release is used only when the sidecar also yields nothing, and is then marked as an estimate unless the latest release is the selected one (see [Resolution semantics](#resolution-semantics)). A pinned release that PyPI does not have keeps its pinned version and takes its license, as an estimate, from the public release of the same number or from the latest release; a pinned release whose lookup fails takes nothing from another release.
- **npm**: `peerDependencies` and `optionalDependencies` are walked alongside `dependencies` (they end up in your installed `node_modules`); `devDependencies` are gated by `--dev`. With a lockfile, optional edges are read in every supported format (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` Classic and Berry, `bun.lock`), so a package reached only through an optional edge is kept together with its own dependencies. A package installed under an npm alias is reported under its real name. A `package.json` dependency whose spec is a git URL (`git+https://…`, `git://…`, an `http(s)` URL ending in `.git`), a hosting shorthand (`github:user/repo`, `gitlab:`, `bitbucket:`, `gist:`, or a bare `user/repo`), or a tarball URL is an [off-registry dependency](#off-registry-dependencies); the `#<commit-ish>` of a git spec is its revision. So is a path spec the scan does not read: `file:`, `link:`, `portal:`, or a bare `../dir` or rooted path. With a lockfile, such a package is read from the lockfile, with the version the lockfile records. `pnpm-lock.yaml`: its origin is the `resolution` (the repository plus the commit, or the tarball URL plus its integrity, or the directory). `package-lock.json` (v2/v3) and `yarn.lock` (Classic): its origin is the `resolved` location, which is a git URL plus the commit in its fragment, a tarball URL plus the entry's `integrity`, or a path; a `link` entry of `package-lock.json` is the directory it links to, and a Yarn Classic entry with no `resolved` line is read from the spec in its header. `package-lock.json` v1 and `bun.lock` put the spec the package was installed from where the version would be; that spec is the origin and the row has no version. Yarn Berry: its origin is the `resolution` protocol, which is a git URL plus `#commit=`, a tarball URL plus the `checksum`, or a `file:` / `portal:` / `link:` path; a `patch:` resolution is read as the package it patches, and a resolution under a protocol licenseal does not know is the origin, as written up to its `#` fragment, plus the `checksum`. A `resolved` location that is a tarball URL in the layout registries serve (`<registry>/<name>/-/<file>.tgz`, on any host) or a `https://npm.pkg.github.com/download/…` URL is a registry package from another registry, looked up on registry.npmjs.org; any other `resolved` tarball URL is off-registry, and so is every tarball URL written as a spec, whatever its layout. A lockfile does not clear what the manifests declare: when every `package.json` that declares a dependency gives it a git or URL spec, or a path spec the scan does not read, and the lockfile lists that name as a registry package, the row keeps the declared origin and stays UNKNOWN. A `workspace:` package, and a `file:` / `link:` / `portal:` directory the scan reads, is the project's own code and is not reported; an archive (`file:pkg.tgz`) is a row wherever it lies. In monorepos and pnpm workspaces, packages defined locally by another `package.json` in the tree are filtered out (they aren't published); a stderr line reports how many were excluded.
- **Rust**: without a `Cargo.lock`, the registry walk does not follow the optional (feature-gated) dependencies of the crates it visits, so a crate enabled only through a feature is not reported; with a `Cargo.lock`, the locked graph is used as-is. A dependency declared with `git = …`, or with a `path = …` the scan does not read (directly, or through a `[workspace.dependencies]` entry), is an [off-registry dependency](#off-registry-dependencies); the origin of a git dependency is the repository plus `rev`, `tag`, or `branch`, in that order of preference. So is a crate that a `[patch.<registry>]` or `[replace]` entry of any `Cargo.toml` in the scanned tree points at a git repository or at such a path, wherever that crate appears in the dependency graph: no crates.io request is made for it. A `registry = "…"` key names another registry, and that crate is looked up on crates.io. With a `Cargo.lock`, a git crate is reported at its locked version with the repository plus the locked commit as its origin. A crate the lockfile gives no `source` is built from a path: it is reported, at its locked version, when a `Cargo.toml` of the scan declares it from, or redirects it to, a path the scan does not read. It is also reported, with `unrecorded source` as its origin, when a `Cargo.toml` of the scan declares it by version only and its name is not a crate of the scanned tree: the lockfile records no path for it, no scanned manifest locates it, and crates.io is not asked about it, whatever version the declaration asks for. A crate locked from another registry (a `registry+…` or `sparse+…` source other than crates.io) is looked up on crates.io, and a `source` of any other kind is the origin as written. The crates.io crates an off-registry dependency pulls in are reported, as `prod` or `dev` by the table that declares it, and name it in `direct_ancestors`; without a `Cargo.lock` they are not reported. A `path` dependency the scan reads is the project's own code and is not reported. When that directory has a `Cargo.toml`, its dependencies come from that file; otherwise, with a `Cargo.lock`, the crates.io crates it pulls in are reported and name it in `direct_ancestors`, and in the table and Markdown reports a crate whose alphabetically-first ancestor is such a path dependency is listed after the direct dependencies and their transitives, because that ancestor has no row to nest it under. A path crate that a `Cargo.lock` reaches only through another path crate the scan does not read, and that no scanned `Cargo.toml` names, is not reported. Without a `Cargo.lock`, a requirement other than an exact `=1.2.3` is resolved against the versions listed in the crate's crates.io record (see [Resolution semantics](#resolution-semantics)); `=` before a version that stops early is such a requirement (`=1.2` is every `1.2.x`, `=1` every `1.x`). That record is the response the latest release is read from, so a range adds no request.
- **Go**: `go.mod` has no general prod/dev distinction — everything in a `require` block ships. The Go 1.24+ `tool` directive is the *only* declarative dev marker (paths there are matched longest-prefix to their module and emitted as `dev`); a `tool` module that a production module also requires is `prod`. `// indirect` is **not** a dev signal. Test-only deps can't be separated from production deps (go.mod doesn't track that). On pre-1.24 projects or projects without `tool` entries, `--dev` and `--no-dev` produce identical reports. With a `go.sum`, the report is its modules plus every requirement in `go.mod` at the version `go.mod` requires. A requirement `go.sum` has no row for (a nested module with no `go.sum` of its own, a module listed only by its `/go.mod` hash, a row for another version) is still reported as a direct dependency; the modules only it requires are reported when a `go.sum` lists them and not otherwise, as in a scan with no `go.sum` at all. Whether that is the whole set depends on the `go` directive. From `go 1.17` on, `go.mod` lists every module needed to build the module's packages and tests, indirect ones included, so its requirements are complete without a `go.sum`. A `go.mod` with a `go` directive below 1.17, or with none (Go reads that as 1.16), lists direct requirements only: when one of its requirements has no `go.sum` row (there is no `go.sum`, or it lacks the row), the modules that requirement depends on are missing from the report, and the `go.mod` is an analysis gap (`lists only direct requirements (its go directive is below 1.17 or absent) and a go.sum row is missing for N of them; …`). Committing an up-to-date `go.sum` removes the gap. Requirements that are not scanned (replaced by a local path, or modules of the workspace) are not counted, and a `--no-transitive` scan records no such gap. No version is chosen among `go.sum` rows: a row for a version other than the required one stays in the report as a separate row. The modules a requirement pulls in (the `direct_ancestors` of a row, and whether it is `prod` or `dev`) are read from the `go.mod` of the required version, wherever `go.sum` lists that version; a module that only another `go.sum` version of it requires is reported as `prod` with no ancestor. `replace` directives in the scanned `go.mod` are applied in the single-line and the `replace ( … )` block form: a requirement replaced by another module is scanned as that module and version, and one replaced by a local path is not looked up anywhere. When the scan reads that path, the module is the project's own code and is not reported, and its own `go.mod` is scanned; any other local path makes it an [off-registry dependency](#off-registry-dependencies), reported under the module's own name with the path as its origin and no version. A directive with a version on its left side (`replace example.org/a v1.0.0 => …`) applies only to a requirement on that version, and takes precedence over a directive for the same module without one. `replace` directives in a dependency's own `go.mod` are not applied (Go honours them only in the main module), and `go.work` `replace` directives are not read. `go.work` `use` directories are followed only when they are relative paths (`..` included); a rooted, drive-qualified, UNC, or device path is never opened and is reported as an analysis gap on `go.work`.
- **Java/JVM**: Maven (`pom.xml`) and Gradle (`gradle.lockfile`, `build.gradle`, `build.gradle.kts`). Per-dep license resolution: (1) the deps.dev `versionbatch` pre-pass for MAVEN; (2) on a batch miss, the POM XML of that version and of the parent POMs it names, from Maven Central; (3) deps.dev v3 single-version GET. Every POM, and the `maven-metadata.xml` version list described below, is requested from Maven Central first and then from two hard-coded fallback registries (`dl.google.com` for Android/Jetpack/Firebase, `repo.jenkins-ci.org` for Jenkins) when Central gives no usable answer for it (a `404`, another error status, or a request that still fails after its retries). Transitive expansion is offloaded to deps.dev's `:dependencies` endpoint, one request per direct dependency. BOM consumers (`<scope>import</scope>`) and the `<dependencyManagement>` parent chain are walked end-to-end (up to 5 levels of parent + 5 of BOM-of-BOM nesting), including `${revision}`-style property inheritance, with and without `--no-transitive`. Maven `compile`/`runtime` map to PROD and `test`/`provided`/`system` to DEV. A `system`-scoped dependency is a JAR on the local filesystem, named by `<systemPath>`: it is an [off-registry dependency](#off-registry-dependencies) with that path, as written, as its origin, and no repository is asked for it. A JAR is not something the scan reads, so the dependency is reported wherever the path points, inside the scanned directory included; an entry with no `<systemPath>` has the origin `unrecorded source`. A `system` scope that comes from `<dependencyManagement>` rather than from the dependency itself is not recognised. Gradle configurations are mapped by a fixed table: `implementation`, `api`, `compile`, `runtime`, `runtimeOnly`, `compileOnly`, `compileOnlyApi`, `compileClasspath`, `runtimeClasspath`, `providedCompile`, `providedRuntime`, the annotation-processor configurations (`annotationProcessor`, `kapt`, `ksp`, `kaptTest`), `releaseImplementation`, `releaseApi`, `releaseRuntimeOnly`, and `shadow` map to PROD; `testImplementation`, `testApi`, `testCompileOnly`, `testRuntimeOnly`, `testCompileClasspath`, `testRuntimeClasspath`, `androidTestImplementation`, `androidTestApi`, `androidTestCompileOnly`, `androidTestRuntimeOnly`, `testFixturesApi`, `testFixturesImplementation`, `debugImplementation`, `debugApi`, `debugRuntimeOnly`, `developmentOnly`, and the code-quality tool configurations (`checkstyle`, `spotbugs`, `pmd`, `detekt`, `jacocoAgent`, `jacocoAnt`) map to DEV. Declarations under any other Gradle configuration name are skipped. Dependencies declared inside Maven `<profiles>` are included from every profile with the same scope mapping; activation conditions (`activeByDefault`, JDK, OS, property) are not evaluated. Profile `<properties>` expand `${…}` tokens in profile-declared dependencies only, and only for names the POM's own `<properties>` do not define. Multi-module reactors filter out in-tree sibling artifacts. Gradle build files are read by a text-parse heuristic that surfaces only static-string `dependencies { … }` declarations, in the Groovy and Kotlin DSLs; a `gradle.lockfile` supplies the resolved versions, and a declaration it does not cover is resolved through the registries. A coordinate declared without a version (`'group:artifact'`, or the map form without `version` — the usual shape when a BOM or a dependency-management plugin supplies versions) is reported at the artifact's latest release when no `gradle.lockfile` covers it. Only a lockfile records the version the build selects, so that version is an estimate and is marked as one (see [Resolution semantics](#resolution-semantics)); its transitive dependencies are expanded from it like those of any other direct dependency. The latest release is the highest version listed in the artifact's `maven-metadata.xml` that is not a prerelease, or the highest prerelease when the artifact has no other version, and never a `-SNAPSHOT`; the list is read from Maven Central, then from the two fallback registries. When none of them lists the artifact, the coordinate is reported with no version and resolves to UNKNOWN. A version that is stated but cannot be resolved (a range, a `${…}` token, a dynamic version) is not replaced by the latest release. A Gradle dynamic version, which is a prefix (`1.+`, `1.2.+`, a bare `+`) or a `latest.*` selector (`latest.release`, `latest.integration`), names a set of versions rather than one: no registry is asked about its literal text, and the coordinate is reported with no version and resolves to UNKNOWN. So do Maven's `RELEASE` and `LATEST` markers, in a `pom.xml` and in a Gradle build file. Every other stated version is resolved as that version, whatever it looks like: a release-train name or a version that starts with a letter (`Aster.SR12`, `r09`, `v1.0`), and a hard requirement on one version, which is Maven's `[1.0]` or Gradle's `1.0!!` and is resolved as `1.0`. Version catalogs, variable interpolation, `platform(...)` / `enforcedPlatform(...)` references, and dynamic blocks are not evaluated (doing so would require running the Gradle configuration phase, which executes scan-target code).
- **.NET**: NuGet (`.csproj` / `.fsproj` / `.vbproj`, `packages.config`, `Directory.Packages.props` for Central Package Management, `Directory.Build.props` / `.targets`, `packages.lock.json`, `project.assets.json`) and Paket (`paket.dependencies`, `paket.lock`). Per-dep resolution: (1) the deps.dev `versionbatch` pre-pass for NUGET; (2) on a batch miss, raw `.nuspec` XML from NuGet flatcontainer — modern `<license type="expression">` parsed directly, legacy `<licenseUrl>` mapped via known-URL-patterns; (3) deps.dev v3 single-version GET. Transitive expansion is lockfile-first (`packages.lock.json` / `project.assets.json` if `dotnet restore` ran; `paket.lock` for Paket), and otherwise a recursive walk of each package's `.nuspec` `<dependencies>` on `api.nuget.org`, up to 32 levels below a direct reference. A version range with no inclusive lower bound and a floating version, in a project file or in a `.nuspec`, are resolved against the package's version list (`api.nuget.org/v3-flatcontainer/{id}/index.json`, one request per package; see [Resolution semantics](#resolution-semantics)). A dependency a `.nuspec` declares with no version, or with one that resolves to no published version (an MSBuild property, a range nothing published satisfies), is reported with no version and resolves to `UNKNOWN`; that, a `.nuspec` that cannot be fetched or parsed, and a package at the 32-level limit are analysis gaps on the project file (see [Output & the CI gate](#output--the-ci-gate)). In `paket.lock`, each package line is reported at its pinned version, whether or not it ends in options such as `- restriction: …` or `- framework: …`; the lines indented under a package are its dependency constraints, not packages. A Paket group named `Test`, `Build`, or `Tools`, or whose name ends in `test`, in any letter case, is dev; every other group, `Main` included, is production. A package that two groups pin at different versions is a row per version, each with the group it is pinned in; pinned at the same version in a dev and a production group, it is one production row. In the `.nuspec` walk every version reached is a row as well: when a project references a package directly and another package depends on a different version of it, both versions are reported, the second as a transitive. Per-TFM graphs are **unioned across all target frameworks** — a Windows-only GPL'd dep still surfaces. With a NuGet lockfile, group and the direct ancestors shown for each transitive follow the lockfile's dependency edges from the references found in the project files: a package reached only from dev references is dev (left out without `--dev`), a dev reference that a production package also depends on is production, and a package that no discovered reference reaches is production. `<PackageReference>` items are read from the project files, from `Directory.Build.props` / `.targets` and the files those import (reported with the `Directory.Build` file as their source), and from every `<When>` / `<Otherwise>` branch of a `<Choose>` block; branch conditions are not evaluated, so the references of all branches are included, and a property defined inside a branch is not used. A project file's own `<Import>` is not followed. A `<GlobalPackageReference>` in `Directory.Packages.props` is a dev dependency, reported with that file as its source. A package whose ID is that of a project in the scanned tree (its `<PackageId>`, or its file name without the extension) is the project's own code and is not reported, whether it appears as a reference, as a lockfile row, or in the `.nuspec` walk; a stderr line reports how many references were excluded. A `<ProjectReference>` is not a NuGet package and nothing is looked up for it: one whose project file lies in a directory the scan reads is the project's own code and is not reported, and any other one is an [off-registry dependency](#off-registry-dependencies) named after the referenced project file, with the path as written as its origin. An `Include` with wildcards (`tests/**/*.csproj`) is judged by the directory its literal part names, the part before the first path segment that holds `*` or `?`: when the scan reads that directory the reference is the project's own code, and otherwise it is one row named by the pattern as written. A `;`-separated `Include` is judged item by item. The path is located with the project file's own `$(Property)` values, `$(MSBuildThisFileDirectory)`, `$(MSBuildProjectDirectory)`, and `$(ProjectDir)`; a path that still holds a `$(…)` token cannot be located, and is the project's own code when the scanned tree has a project file of that name (or one its wildcard file name matches) and is reported otherwise. A `<ProjectReference>` declared in a `Directory.Build` file is not read. Paket `git`, `github`, `gist`, and `http` sources (`paket.dependencies` lines and the `GIT` / `GITHUB` / `GIST` / `HTTP` sections of `paket.lock`) are not reported and nothing is requested for them. CPM `<PackageVersion>` is stitched into versionless `<PackageReference>` entries, and `$(Property)` version tokens are expanded from the project file and the `Directory.Build` files above it; for a reference declared in a `Directory.Build` file both lookups start at that file's directory. `PrivateAssets="all"`, as an attribute or as a `<PrivateAssets>` child element, maps to DEV. So does a `Condition` that is, as a whole, a Debug / Test configuration or IsTestProject comparison (`'$(Configuration)' == 'Debug'`); a condition that combines one with anything else (`'$(Configuration)' == 'Debug' Or '$(Configuration)' == 'Release'`) is production. The rule is applied to the reference's own `Condition` and to the `Condition` of its enclosing `<ItemGroup>`, in project files, in `Directory.Build` files and the files they import, and inside `<Choose>` branches: a reference is DEV when either one is such a condition, so test packages declared in an `<ItemGroup Condition="'$(IsTestProject)' == 'true'">` are DEV. `nuget.config` `<packageSources>` are NOT honored (no NuGet source other than `api.nuget.org` is queried). `<Import Project="…">` chains in `Directory.Build.props` / `.targets` are followed only for relative paths (`..` included); a rooted, drive-qualified, UNC, or device path is never opened and is reported as an analysis gap on the importing file.
- **PHP**: Composer (`composer.json`, `composer.lock`). **Lockfile-first**: composer.lock entries embed a structured SPDX `license` field, so the resolver answers from the lockfile without HTTP when the pin matches. Falls back to Packagist's `/p2/{vendor}/{package}.json` per-version metadata for manifest-only mode. A constraint is resolved against the versions that response lists (see [Resolution semantics](#resolution-semantics)); a locked or exact version it does not list resolves to `UNKNOWN`, never to the license of another release. Group attribution follows the lockfile: an entry listed under `packages-dev`, or one that carries `dev: true`, is dev. Platform pseudo-packages (names without a `/`: `php`, `ext-*`, `lib-*`, `hhvm`) are filtered out; a `vendor/package` name is always scanned, including vendors that start with `php-`, `ext-`, or `lib-`. [Off-registry dependencies](#off-registry-dependencies) are read from `composer.lock` and from the `repositories` of `composer.json`. In `composer.lock`, an entry whose `dist` or `source` has the type `path` is a path package: not reported when the scan reads that path, reported with the path as its origin otherwise, and reported with the origin `unrecorded source` when it records no path. An entry whose `source.url` is the URL of a version-control repository that the `composer.json` beside the lockfile declares (`vcs`, `git`, `github`, `gitlab`, `bitbucket`, `git-bitbucket`, `forgejo`, `hg`, `svn`, `fossil`, `perforce`), and an entry whose name a `package` repository there defines, is off-registry: its origin is the repository plus the locked `source.reference`, or the `dist` URL plus its `shasum` when it has no `source`. An entry with no `source` whose `dist` URL is a filesystem path is an archive from an `artifact` repository, and is off-registry with that path as its origin. Two spellings of one repository (`https://host/a/b.git`, `git@host:a/b`) match. The license the lockfile records for an off-registry entry is not used. Every other lockfile entry is a Packagist package: `composer.lock` records a `source` repository for Packagist packages too, so an entry is not taken off the registry by its `source` alone, and a `composer.lock` with no `composer.json` beside it yields only its path entries and its `artifact` archives as off-registry. Without a `composer.lock`, a requirement that a `package` repository defines inline is off-registry (origin: its `source` plus `reference`, or its `dist` URL plus `shasum`), and a requirement on a package of the scanned tree that a `path` repository holds (`packages/*` wildcards included) is the project's own code and is not reported. **Not determined without a `composer.lock`:** `composer.json` does not say which packages a version-control repository, an `artifact` repository, or a `path` repository the scan does not read, provides (Composer learns that by reading the repository), so a requirement such a repository satisfies is looked up on Packagist by name and gets the license of the Packagist package of that name, or `UNKNOWN` when there is none. That `composer.json` is reported as an [analysis gap](#output--the-ci-gate), which fails `--strict`. Scan with the `composer.lock` to have the package reported as off-registry and the gap closed. A `composer` repository is another registry: its packages are looked up on Packagist. No deps.dev pre-pass and no batch endpoint, so the lockfile-first design minimises load on this donation-funded registry.
- **Ruby**: RubyGems (`Gemfile`, `*.gemspec`, `Gemfile.lock`). deps.dev `RUBYGEMS` batch runs first to amortise load; rubygems.org v2 per-version / v1 latest fills the gap. A gem with no locked version is reported at its latest release when the declared requirement allows that release. When it does not, the gem's version list (`/api/v1/versions/{name}.json`) is requested, once per gem, and the gem is reported at the highest release the requirement allows (see [Resolution semantics](#resolution-semantics)). `licenses` is a structured SPDX array. A gem that is not from rubygems.org is an [off-registry dependency](#off-registry-dependencies): a `GIT` or `PLUGIN SOURCE` spec in `Gemfile.lock` (origin: `remote` plus `revision`), a `PATH` spec the scan does not read, and a `Gemfile` gem declared from a repository or a path: by an inline `git` / `github` / `gist` / `bitbucket` / `path` option, in the keyword (`git: "…"`) or the hash-rocket (`:git => "…"`) spelling, or by an enclosing `git "…" do`, `github "…" do`, `gist "…" do`, `bitbucket "…" do`, or `path "…" do` block (origin: the repository plus `ref`, `tag`, or `branch`, in that order of preference). A gem's own source option takes precedence over the block around it. A source whose repository or path is not a string literal (`git REPO_URL do`) still takes its gems off the registry, with the origin `unrecorded source`. A `source "…" do` block names another gem server: its gems are looked up on rubygems.org. A gem declared from a path the scan reads, and a `PATH` spec at such a path, is the project's own code and is not reported; a gem under `vendor/` is not one the scan reads. A `Gemfile` gem is dev only when every group it belongs to is `:development` or `:test`; a gem in any other group (`:production`, `:staging`, or a custom group such as `:assets`), in a mixed list (`group :production, :test`), or in no group is production. Group options such as `optional: true` are not group names, and nested `group` blocks and a per-line `group:` / `groups:` add up. A group name is read from a `:symbol`, a quoted string (`group "test"`, `group: "test"`), or a `%i[...]` / `%w[...]` word list in any bracket delimiter (`groups: %i[development test]`, `group *%w[development test]`); a name written any other way (a constant, a method call, a word list combined with another expression) is treated as production. A gemspec `add_development_dependency` is dev.
- **Hex (Elixir/Erlang)**: Mix (`mix.exs`, `mix.lock`), rebar3 (`rebar.config`, `rebar.lock`), erlang.mk (`Makefile`). hex.pm-only (deps.dev doesn't index Hex); license from the structured `meta.licenses` array. hex.pm keeps that array per package, not per release, and overwrites it each time a release is published: it is the license of the release published last, and the license reported for any other release, an older pin included, is marked as an estimate (see [Resolution semantics](#resolution-semantics)). A requirement with no locked version is resolved against the releases listed in the package response the license is read from, with no further request (see [Resolution semantics](#resolution-semantics)). Dev attribution: a `mix.exs` dep whose `only:` does not include `:prod` (`only: :dev`, `only: [:dev, :test]`, `only: :docs`), the rebar `test` / `dev` profiles, and erlang.mk `TEST_DEPS`, `BUILD_DEPS`, `DOC_DEPS`, and `SHELL_DEPS` (`DEPS` and `REL_DEPS` are production; `LOCAL_DEPS` is not read). Dependencies declared under any other `rebar.config` profile (`prod`, or a custom name) are production, alongside the top-level `{deps, …}` term; a `{deps, …}` list inside an `overrides` entry is not read. A dep that is not a hex.pm package is an [off-registry dependency](#off-registry-dependencies): a `mix.lock` entry that is not a `:hex` tuple (`:git`: the repository plus the locked commit; `:path`: the path, when the scan does not read it), `git:` / `github:` / `path:` in `mix.exs` (the repository plus `ref:`, `tag:`, or `branch:`; the key may also be quoted, `"git": …`, or the first element of a pair, `{:git, …}`), every source tuple but `{pkg, …}` in `rebar.config` and `rebar.lock` (`{git, …}` / `{git_subdir, …}` / `{hg, …}`, and any other tuple whose first argument is a quoted location, such as `{svn, "…"}`: the repository plus `{ref, …}`, `{tag, …}`, or `{branch, …}`; `{path, …}`: the path; a tuple with no such location: `unrecorded source`), and an erlang.mk `dep_<name>` fetched with `git`, `git-subfolder`, `hg`, `svn`, `cp`, or `ln`. `in_umbrella: true`, and a `path:` / `{path, …}` / `cp` / `ln` path the scan reads, are the project's own apps and are not reported. hex.pm allows 100 unauthenticated API requests per minute and has no batch endpoint, so a project with more than 100 Hex packages pauses each time the limit is reached until hex.pm's reported reset time (up to about a minute per further 100 packages), then continues. Each pause is announced on stderr when it starts, once, with its length (`hex.pm rate limit reached: pausing hex.pm requests for 41s until it resets.`), on a terminal and in a log alike. The waiting is bounded: it stops after three pauses in a row with no response other than a `429` in between, or after ten full-length pauses in total, and packages still rate limited after that resolve to UNKNOWN. When that happens, a `Warning:` line at the end of resolution gives the number of hex.pm lookups that were abandoned: a package whose license lookup was abandoned is the UNKNOWN row, and one whose dependency lookup was abandoned (a scan with no `mix.lock` / `rebar.lock`) is reported without its own dependencies.
- **R / CRAN**: `DESCRIPTION` (`Imports` / `Depends` / `LinkingTo` prod; `Suggests` / `Enhances` dev) and `renv.lock` / `packrat.lock`. The official CRAN `PACKAGES` index is fetched once per scan; license and transitive closure resolve locally from it. The index lists the current version of each package only: a package that `renv.lock` / `packrat.lock` pins to another version is reported at the pinned version with the license of the current one, marked as an estimate (see [Resolution semantics](#resolution-semantics)). R's license grammar (`GPL (>= 2)`, `MIT + file LICENSE`) is translated to SPDX (a bare `file LICENSE` with no preceding token → UNKNOWN). A package a lockfile does not source from CRAN is an [off-registry dependency](#off-registry-dependencies): in `renv.lock`, `GitHub` / `GitLab` / `Bitbucket` (origin: the repository plus `RemoteSha`, or `RemoteRef` when no commit is recorded), `git`, `URL`, and `Local` (the `RemoteUrl`); in `packrat.lock`, `github` / `gitlab` / `bitbucket` and `source` (the `SourcePath`). Bioconductor is not CRAN: its packages are reported with the origin `Bioconductor`. An entry that records no locator has its source label as origin. A dependency named by the `Remotes` field of `DESCRIPTION` (`user/repo`, `github::`, `gitlab::`, `bitbucket::`, `git::`, `svn::`, `url::`, `local::`, `bioc::`) is off-registry too, and a lockfile row for it that records no source of its own takes that origin; the package a remote provides is the name before `=` when the entry has one, otherwise the repository, archive, or directory name. A `Local` / `source` / `local::` path the scan reads is the project's own code and is not reported; a source archive is a row wherever it lies.
- **Cycles**: detected via `(ecosystem, name, version)` visited-set; cycles terminate cleanly.
- **Depth cap**: `--max-depth 50` by default. It bounds the registry walks of step 2 (Python, npm, Rust, PHP, Ruby, Hex): reaching the cap emits a stderr warning and stops expansion past that level. It is not an analysis gap. It does not bound a lockfile's graph, the deps.dev graph of a Maven or Gradle dependency, the NuGet `.nuspec` walk (which has its own fixed limit of 32 levels), the CRAN index closure, or the Go module graph.
- **Unread dependency lists**: a package whose dependencies the registry did not give is still reported, and is recorded as an analysis gap on the manifest of the direct dependency that leads to it (see [Output & the CI gate](#output--the-ci-gate)). Applies to the registry walks of step 2, the deps.dev graph of a Maven or Gradle dependency, and the NuGet `.nuspec` walk.

## Resolution semantics

- Exact pins (`==2.28.1`, `18.2.0`) are reported at that exact version. The license is read from that release's own metadata wherever a registry serves it per release; where it does not, the license is marked as an estimate (see the two points on license sources and license estimates below). In npm, one complete version behind `=` or a `v` prefix (`=18.2.0`, `= 18.2.0`, `v18.2.0`) is the same exact pin as the bare version; a partial one (`=18.2`) is a range. In Cargo, `=1.2.3` is an exact pin, and a partial `=1.2` or `=1` is a range that is resolved, and marked as an estimate, like any other.
- Empty version constraints resolve against the registry's latest published release. That includes a Gradle coordinate declared with no version when no `gradle.lockfile` covers it. A NuGet reference with no version, and a `pom.xml` dependency with no version that the parent chain does not manage either, are the exception: each is reported with no version and resolves to `UNKNOWN`.
- A range resolves to the highest published release inside it, read in the grammar of its ecosystem: PEP 440 specifiers for Python (`>=`, `<=`, `!=`, `~=`, `==1.2.*`); npm ranges (`^`, `~`, comparisons, hyphen ranges, `||`, `x` / `*` wildcards); Cargo requirements (a bare `1.2` means `^1.2`; `^`, `~`, `*` / `x` wildcards, comparisons joined by commas); RubyGems requirements (`~>`, `>=`, `>`, `<=`, `<`, `!=`, `=`, several together); Hex requirements (`~>`, comparisons, `and` / `or`); Composer constraints (`^`, `~`, `*` / `x` wildcards, comparisons joined by a space or a comma, alternatives joined by `|` or `||`, hyphen ranges, an `@stability` flag, a `v` prefix). A prerelease is selected only when the range admits prereleases and no release is inside it. In an npm or Cargo range every comparator has to hold, and a prerelease is inside the range only when a comparator names a prerelease of the same release: `>=2.0.0-rc.1 <2.0.0` selects `2.0.0-rc.2`, never `2.0.0`, and `<2.0.0` selects no prerelease of `2.0.0`. Python follows pip instead: a specifier that itself names a prerelease (`>=1.0a1`) selects the highest version inside it, prerelease or not, and a prerelease is also selected when no release is inside the range. Yanked crates are not selected. The registry's latest release is reported only when it is inside the range.
- A NuGet range resolves as NuGet restores it, to the lowest version inside it. A bare version is an inclusive minimum, so `1.2.3`, `[1.0,2.0)`, and `[1.0,)` resolve to their lower bound without a registry lookup. A range whose lower bound is exclusive or absent (`(1.0,2.0]`, `(,2.0]`) resolves to the lowest published release inside it, and a floating version (`1.*`, `*`) to the highest published release it matches.
- Not resolved to a version, and reported as `UNKNOWN` with no version: a constraint that is not written in its ecosystem's grammar; a range that no published version satisfies; an exact Composer version that Packagist does not list; a Composer branch constraint (`dev-main`, `1.x-dev`); a Maven or Gradle version range, dynamic version, or `RELEASE` / `LATEST` marker (`[1.0,2.0)`, `1.+`, `latest.release`); a NuGet version holding an unresolved MSBuild property. No constraint falls back to the latest release or to the first entry of a registry response. A direct dependency that does not resolve is always a row. Requirements on one package that do not resolve share one row, whatever their constraints: the row of the first direct declaration among them, production when any of them is. A transitive requirement that does not resolve is a row unless a resolved version of the same package satisfies it, or cannot be compared with it; it is then that row, which lists the requirement's direct ancestors too. A requirement that no resolved version satisfies (`>=2,<3` beside a resolved `1.0`) stays an `UNKNOWN` row of its own, and so does a dependency of the same name with an [origin](#off-registry-dependencies).
- Go and R have no range to resolve. `go.mod` names exact versions. A `DESCRIPTION` constraint (`(>= 1.0)`) is not evaluated: the CRAN index lists one version of each package, and that version is the one reported.
- A version that licenseal picked from a registry is an estimate and is marked as one: `~1.2.3` in the table and Markdown formats, with one legend line under the table when any row is marked, and `"estimated": ["version"]` in JSON. Marked: every transitive row a registry walk adds; a direct dependency declared with a range or with no constraint, with or without `--no-transitive`; Maven and Gradle transitives taken from the deps.dev dependency graph; a Gradle coordinate declared with no version, reported at its latest release; NuGet rows from the `.nuspec` walk and direct references declared with a range; and R rows resolved from the CRAN index. Not marked: a row a lockfile supplies, an exact pin in a manifest (`==2.28.1` in Python, `18.2.0`, `=18.2.0`, or `v18.2.0` in npm, `=1.2.3` in Cargo, a bare version or `= 1.2.3` in RubyGems, a bare version or `== 1.2.3` in Hex, a bare version in Composer, a bare version or `[1.2.3]` in NuGet, a Maven version that is stated or managed by the parent chain), and every Go version, since `go.mod` and `go.sum` name exact versions. A dependency reported with no version has nothing to mark, and an [off-registry dependency](#off-registry-dependencies) is never marked: no registry is asked about it, so the version shown for it is the one its lockfile records.
- Where the license of a pinned release comes from, per ecosystem. **Python**: that release's own PyPI JSON, then its wheel metadata; when neither declares a license, the project's latest release. A pinned release PyPI does not have (it answers `404`: a build published on another index, a `+local` version) is still reported at its pinned version, with the license of the closest release PyPI does have: the public release of the same number for a `+local` version (`1.2.3` for `1.2.3+internal`), read the same way, otherwise the project's latest release. A lookup of the pinned release that fails (a server error, a timeout, or a connection error after the retries, or any error status other than `404`) borrows nothing from another release: the dependency is `UNKNOWN` at its pinned version, unless deps.dev has that exact version. **npm**: that version's registry document. **Rust**: that version's crates.io record. **Go**: the deps.dev record of that module version. **Java/JVM**: that version's POM and the parent POMs it names, then the deps.dev record of that version. **.NET**: that version's `.nuspec`, then the deps.dev record of that version. **PHP**: the `composer.lock` entry, otherwise that version's Packagist entry. **Ruby**: that version's rubygems.org record. **Hex**: the package's one `meta.licenses` array, which hex.pm overwrites each time a release is published, so it is the license of the release published last. **R**: the CRAN index, which lists the current version of each package and its license. The deps.dev batch that answers first for Python, npm, Rust, Go, Java, .NET, and Ruby is per version.
- A license read from metadata that describes another release than the reported one is an estimate and is marked as one: `~MIT` in the table and Markdown formats (the mark precedes the whole expression), under the same legend line as an estimated version, and `"license"` in the JSON `estimated` array (`["license", "version"]` when both are estimates). Marked: an R package that `renv.lock` / `packrat.lock` pins to a version other than the one the CRAN index lists; a Hex package reported at any release but the one published last, which is the highest version unless a release on an older line followed it (a release list in which not every entry carries its publication time marks every release); a Python release that declares no license of its own and takes the one of the project's latest release, unless that latest release is the reported one; and a pinned Python release PyPI does not have, whose license is read from the public release of the same number or from the latest release. Not marked: a license read from the reported release's own metadata, which is every npm, Rust, Go, Java, .NET, PHP, and Ruby row and every row deps.dev answers; a license a review supplies; and an `UNKNOWN` license, which names nothing to qualify. A license estimate is not a finding and not an analysis gap, and it does not fail strict mode by itself. The license is judged like any other: an estimated `GPL-3.0-only` in an MIT project is a violation.
- A registry lookup that cannot produce a license resolves that one dependency to `UNKNOWN` and the scan continues. A failed lookup of a pinned release is never answered with the metadata of another release. This covers an HTTP 200 whose body is not a JSON object, a license, version, or metadata field of an unexpected type (well-formed fields beside it are still read), and a dependency name or version that cannot be put in a request, such as one containing an ASCII control character or a lone surrogate (an unpaired `\uD800`–`\uDFFF` escape in a JSON manifest or registry response). A lookup never strips or rewrites the name to make the request succeed; the dependency is reported under the name it was discovered with. A response that is not a JSON object and a request that cannot be built count as failed lookups under the every-lookup-fails rule in [Output & the CI gate](#output--the-ci-gate): a scan in which no lookup succeeds and nothing resolves still ends with that error.

licenseal is a license resolver, not a dependency resolver. It does not evaluate Python environment markers, `Requires-Python`, npm `engines`, or transitive-version conflict resolution beyond first-encountered-wins. That keeps resolution fast and predictable but does not model environment-specific installability.

## License expressions

How a declared license string is read before the matrix and the pair-level overrides in the [README](README.md) apply.

- **`WITH` exceptions.** The text after `WITH` is matched whole and case-sensitively against a fixed list; a name that only starts like a listed exception does not match. `Classpath-exception-2.0` and `Classpath-exception-2.0-short` on a GPL license make the term weak copyleft, and the pair-level rules of the bare GPL license do not apply to it (`GPL-3.0-only WITH Classpath-exception-2.0` is compatible in a `GPL-2.0-only` project). An exception that only adds a permission leaves the term judged as its bare license, pair-level rules included, so `Apache-2.0 WITH Swift-exception` in a `GPL-2.0-only` project is a violation like `Apache-2.0`; these are `Autoconf-exception-2.0`, `Autoconf-exception-3.0`, `Bison-exception-2.2`, `Bootloader-exception`, `Font-exception-2.0`, `GCC-exception-2.0`, `GCC-exception-3.1`, `Libtool-exception`, `Linux-syscall-note`, `LLVM-exception`, `OCaml-LGPL-linking-exception`, `Swift-exception`, `Universal-FOSS-exception-1.0`, and `WxWindows-exception-3.1`. One of them also lifts one pair-level rule: `Apache-2.0 WITH LLVM-exception` is compatible in a `GPL-2.0-only` project, because the LLVM exception lets a recipient waive the Apache-2.0 sections that conflict with GPLv2 when the code is combined with GPLv2 code. It lifts no other rule: `GPL-3.0-only WITH LLVM-exception` in a `GPL-2.0-only` project is a violation, and so is a bare `Apache-2.0` operand beside the term. Any other text after `WITH` is read as terms nobody evaluated, applying on top of the license before it the way `<license> AND` an unresolved license does: what follows `WITH` in a registry field can restrict use as well as permit it, so it never lowers a verdict. The term is a violation when its bare license is one, by risk class or by a pair-level rule (`GPL-3.0-only WITH Qt-GPL-exception-1.0` in an MIT project, `Apache-2.0 WITH Commons-Clause` in a `GPL-2.0-only` project), and when the term is the whole license the reason names the exception that was not judged. Otherwise it is unknown, never compatible and never a warning (`Apache-2.0 WITH Commons-Clause` and `MIT WITH GPL-3.0-only` in an MIT project, `GPL-3.0-only WITH Classpath-exception-3.0` in a `GPL-3.0-only` project). Its risk level is that of the bare license when that is strong or network copyleft, and unknown for any other license. In an `AND` such a term sends the dependency to review unless an operand is a violation; in an `OR` the other choices stay open. The reason of a dependency sent to review this way names the exception that was not evaluated, whether the term is the whole license or one operand of a compound (`MIT AND Apache-2.0 WITH Commons-Clause`), or, when another operand is a copyleft license the project can take, the whole term as one the consumer cannot avoid. A project license with an unrecognized exception is read the same way: a strong or network copyleft license keeps its matrix row and its pair-level rules (`GPL-2.0-only WITH` an unrecognized exception is judged as a `GPL-2.0-only` project), and any other license is not a recognised project license: the project is checked as `Proprietary`, with the warning described under [Project license](#project-license).
- **Operands that did not resolve.** In an `AND` every operand binds. One that is a violation makes the dependency a violation whatever the other operands are (`GPL-3.0-only AND UNKNOWN`, or `GPL-3.0-only AND` a license licenseal does not recognize, in an MIT project); when no operand is a violation, one that did not resolve makes the dependency unknown. In an `OR`, a choice that did not resolve is never the one taken, and the fully recognized choices stay open (`MIT OR CustomLicense` is judged as `MIT`).
- **Malformed expressions.** A string made of license IDs, `OR` / `AND` / `WITH`, and parentheses that do not fit together — an operator with an operand missing (`MIT AND GPL-3.0-only AND`, `MIT OR AND GPL-3.0-only`), or parentheses that do not pair up around the IDs (`MIT OR (GPL-3.0-only`) — is reported with the license `UNKNOWN`. Its verdict comes from every license it names applying together, plus one operand that could not be read: its `OR` is not read as a choice. So it is a violation when a license it names is one (both examples, in an MIT project, with or without `--no-strict`), unknown otherwise, and never compatible. A license directly before or after a dangling `WITH` does not count as named. A string with any other content is not searched for license IDs and stays unknown. Whitespace just inside a parenthesis is not an error: `( MIT OR ISC ) AND Zlib` is `(MIT OR ISC) AND Zlib`.
- **Operators are kept as written.** `GPL-3.0-only AND LGPL-3.0-only` in a registry license field, in the licenses of a Maven POM (several `<license>` entries are joined with `AND`), or in a review entry is both licenses, and `CDDL-1.0 AND GPL-2.0-with-classpath-exception` is both of those.
- **deps.dev license arrays.** A deps.dev answer is a `licenses` array. One entry is read as the expression it is. For a RubyGems package the array repeats the gem's own `licenses` field and is read as a list the source does not define (below). For every other system, several entries are the license texts deps.dev found in the package and all apply (`AND`), with two rewrites that are made for such an array and for nothing else: a GPL entry beside an LGPL entry of the same version (or GPL-2.0 beside LGPL-2.1) is the text the LGPL refers to and is dropped, and exactly one CDDL entry plus `GPL-2.0-with-classpath-exception` is that dual license and is read as `OR`. `license_raw` shows the array as received, joined with `AND`. An array that contains deps.dev's `non-standard` marker (a license text deps.dev could not classify), alone or beside other entries, is not an answer: `["Apache-2.0", "non-standard"]` is not reported as `Apache-2.0`. The dependency is then resolved from its own registry, as when deps.dev has no license for it; a Go module, for which deps.dev is the only source, is unknown.
- **License lists.** When a source gives several licenses for one package, the list is read by what that source defines:
  - **A choice**, by the source's own definition: a Composer `license` array (`composer.lock`, Packagist); `/` in a Cargo `license` field; `|` in an R `License` field; npm's legacy `licenses` array; `OR` in an SPDX expression.
  - **All apply**: several `<license>` entries in a Maven POM; a deps.dev `licenses` array with several entries (above), other than a RubyGems one; `AND` in an SPDX expression.
  - **Not defined by the source**: a RubyGems `licenses` array with more than one entry, whether rubygems.org or deps.dev answers; a Hex `meta.licenses` array with more than one entry; several distinct PyPI license classifiers on one release; and a comma- or slash-separated list inside one license string from any source (`MIT, GPL-3.0-only`, `MIT/Apache-2.0`), other than `/` in a Cargo license and other than an R `License` field, where `|` is the only list separator and a list written with a comma or a slash is reported with the license `UNKNOWN`.
- **A list the source does not define is judged twice**, once as a choice and once with every entry applying. When both readings give the same verdict, that verdict is reported: `MIT/Apache-2.0` from npm in an MIT project is compatible. When they differ, the verdict is `unknown`; the reason gives the result of each reading and asks you to confirm which holds and record that expression in `licenseal.review.toml`. A RubyGems `["MIT", "GPL-3.0-only"]` in an MIT project is unknown (compatible as a choice, a violation if both apply), and so is `MIT/Apache-2.0` from PyPI in a `GPL-2.0-only` project, where `Apache-2.0` conflicts. The report shows the list as a choice (`GPL-3.0-only OR MIT`), and `license_raw` shows an array as a comma-separated list. A review entry is an expression you wrote and is judged as written.
- **A list with an entry licenseal does not recognize.** A comma- or slash-separated list in one license string where an entry is not a license licenseal recognizes (`GPL-3.0-only, acme internal license`) is reported with the license `UNKNOWN`, and a source that has another license field to fall back on still uses it. The verdict comes from both readings of the list, with the unrecognized entry as a license that did not resolve. It is a violation when it is one under both readings, which is when every recognized entry is a violation in the project, by risk class or by a pair-level rule: that example in an MIT project, with or without `--no-strict`, and the reason quotes the declared string. In every other case it is unknown: `MIT, acme internal license` in an MIT project is compatible as a choice and unknown when both apply. It is never compatible. An unrecognized entry of a RubyGems or Hex array, or an unmapped PyPI license classifier, is judged the same way, and there the report shows the list (`MIT OR UNKNOWN`).
- **One pair is a choice by the license's own terms**, in any such list: exactly `Ruby` and `BSD-2-Clause` and nothing else, because the Ruby license offers the 2-clause BSD license as an alternative to its own conditions. `["Ruby", "BSD-2-Clause"]` is judged as `BSD-2-Clause OR Ruby` only; any other list that contains `Ruby` is judged under both readings, and `Ruby` on its own is unknown.
- **PyPI license classifiers.** When a release has no usable `license_expression` or `license` field, its `License ::` trove classifiers are read, all of them. One classifier is that license. Several distinct ones are a list PyPI does not define and are judged under both readings: `BSD License` beside `GNU General Public License v3 (GPLv3)` is unknown in an MIT project. `License :: Other/Proprietary License` is an entry of the list like any other and reads as `Proprietary`; a license classifier licenseal has no mapping for is an entry that did not resolve. The category classifiers `License :: OSI Approved` and `License :: DFSG approved` name no license and are left out. A `license` field that declares a proprietary license is kept, and no classifier replaces it; a placeholder (`UNKNOWN`) or a pointer to a bundled file (`LICENSE.txt`, `SEE LICENSE IN …`) still falls through to the classifiers.
- **R `+ file LICENSE`.** In an R license such as `MIT + file LICENSE`, the file is never fetched or read. After `MIT`, `BSD_2_clause`, or `BSD_3_clause` it is the copyright notice those license templates require, and the result is the license alone. After any other license it holds terms that restrict or extend that license, so a dependency declared `Apache License (== 2.0) + file LICENSE` or `GPL-3 + file LICENSE` is reported as `Apache-2.0 AND UNKNOWN` or `GPL-3.0-only AND UNKNOWN`: unknown, or a violation where the named license is one by itself. For the scanned project's own `DESCRIPTION` license the named license alone is used.
- **The project's own license.** A project license with a top-level `OR` is every license the project distributes under, and a dependency has to be compatible with each arm. An arm licenseal does not recognize is not dropped: it is judged as a `Proprietary` arm, the strictest one, so `AGPL-3.0-only OR Commercial` flags a `GPL-3.0-only` dependency as a violation exactly as `AGPL-3.0-only OR Proprietary` does. A project license that licenseal does not recognize as a whole (no `OR`) is not used: the project is checked as `Proprietary`, with the warning described under [Project license](#project-license).
- **Not a list.** A string that mixes a list separator with `and` / `or` (`MIT/Apache-2.0 and GPL-3.0-only`), a list inside a list (`MIT, Apache-2.0/GPL-3.0-only`), and a URL that licenseal does not recognize, whatever its path spells, are not split and are unknown.

## Discovery: auto-skipped directories

The walker skips a unified set of directory names at every depth — same list for all ecosystems:

- **VCS / caches**: `.git`, `.tox`, `.nox`, `__pycache__`, `node_modules`
- **Sample / fixture trees**: `examples`, `fixtures`, `__fixtures__`
- **Build / dist / vendoring outputs**: `build`, `dist`, `target`, `.eggs`, `site-packages`, `vendor`, `__pypackages__`, `.pdm-build`
- **JS framework build outputs & legacy package-manager trees**: `.next`, `.nuxt`, `.svelte-kit`, `.yarn`, `bower_components`, `jspm_packages`

Virtualenvs are detected **structurally** via the PEP 405 `pyvenv.cfg` marker rather than by name, so `.venv/`, `venv/`, `env/`, `env-3.11/`, and any other naming convention are skipped without false positives. Any subdirectory with its own `.git` (file or directory) is skipped automatically — cloned dependencies, vendored forks, and submodules are treated as separate projects. A symlinked directory is not entered. Use `--exclude-dirs` for subtrees not already covered.

## Off-registry dependencies

A dependency whose source is a **git repository**, a **direct URL** (a wheel, an sdist, a tarball), or a **path the scan does not read** does not come from a package registry. One policy applies in every ecosystem:

- It is reported as one row whose license is `UNKNOWN`. No registry request is made for it under any name, and nothing is downloaded: a registry package of the same name is a different package, and a private name is never sent to a public registry. The row fails strict mode until it is reviewed.
- Its JSON `origin` field names the source in one string, as specific as the files allow: `git+<url>@<commit>` when a lockfile records the commit, otherwise `git+<url>@<ref>` for a declared tag, branch, or revision, otherwise `git+<url>`; `<url>#<hash>` for a direct URL with a recorded hash, otherwise `<url>`; a path as written. Credentials are removed first: the user-info part of a URL (`https://token@host/…`) and its query string never reach a report. A lockfile entry that records no locator has the lockfile's own source label as origin, or `unrecorded source`.
- `resolved_version` is the version a lockfile records for it, empty otherwise. `package_url` is empty.
- In the table and Markdown reports the row's line under **Details** reads `<name> comes from an off-registry source (<origin>); its license is not looked up — manual review required`, and a reviewed row shows `UNKNOWN (source: <origin>)` as its detected license. `check` counts these rows on a stderr line of their own (`Warning: N package(s) come from an off-registry source and were not looked up.`); they are not part of the count of packages that `could not be resolved from registries`, which covers failed lookups only.
- A path dependency is the project's own code only when **the scan reads it**: the path resolves to a directory inside the scanned directory that the scan walks. It is not reported, and the manifests in that directory are scanned like any other. Every other path is one the scan does not read, and is a row with the path as written as its origin: a path outside the scanned directory; an archive file wherever it lies (a wheel, an sdist, an npm tarball, a JAR); a directory the scan does not walk (one under a directory name skipped at every depth, such as `vendor/`, `node_modules/`, `examples/`, or `fixtures/`; a nested repository or submodule; a virtualenv; an `--exclude-dirs` path); and a path that does not exist. A rooted, drive-qualified, UNC, or home-relative path is never resolved against the filesystem and is reported as written.
- **Not read:** a declaration that redirects a registry package to another source from outside the package's own entry. These are npm `overrides`, Yarn `resolutions`, and pnpm `overrides` in `package.json`; `[tool.uv]` `override-dependencies` and `constraint-dependencies`; a Maven `system` scope that a `<dependencyManagement>` entry supplies; and Cargo's `.cargo/config.toml` (`[patch]`, `paths`, source replacement). A package that only such a declaration takes off the registry is looked up on the registry under its name, unless a lockfile records a git, URL, or path source for it.
- When a lockfile records the registry packages an off-registry dependency pulls in, those are reported and name it in `direct_ancestors`.
- A package that one manifest declares off-registry and another declares as a registry requirement is two rows, with or without a lockfile: the registry row, at the version a lockfile holds for it, and the off-registry row with its origin. A lockfile that lists only the registry package does not stand for the off-registry declaration.
- An **alternate index or registry** is not an off-registry source. A package pinned to a Poetry `source`, a uv index, a `Gemfile` `source` block, a Cargo `registry`, a private npm registry, or carrying a `+local` version from an internal mirror is looked up on the public registry under the same name, and the license of the public package is what is reported (see [SECURITY.md](SECURITY.md#what-leaves-the-process)). A Python build that PyPI does not have is reported at its pinned version, and the public package's license is marked as an estimate for it (see [Resolution semantics](#resolution-semantics)).

Which declarations are read as off-registry is listed per ecosystem under [Per-ecosystem resolution detail](#per-ecosystem-resolution-detail). To clear such a row, review it by its source: see [Manual review file](#manual-review-file).

## Manual review file

When a dependency is flagged but you have better license information than the resolver (e.g. you've read the bundled `LICENSE` file), record the override in `licenseal.review.toml` at the project root:

```toml
[[review]]
ecosystem = "python"
package = "mystery-lib"
version = "1.0.0"
license = "MIT"
note = "confirmed from packaged LICENSE file"
```

Workflow:

1. `licenseal check -f json -o report.json` — capture flagged deps
2. `licenseal init-review-file --from-report report.json` — scaffold blank entries offline
3. Fill in `license` (and optionally `note`) for each entry
4. `licenseal check` again — overrides apply

`licenseal init-review-file` without `--from-report` does steps 1 and 2 in one go: it runs the scan `check` runs by default and scaffolds an entry for each flagged dependency, direct or transitive.

An [off-registry dependency](#off-registry-dependencies) has no registry version to key a review on, so its entry is keyed on its source. The stanza carries a `source` key holding the row's `origin` string, and `version` is optional:

```toml
[[review]]
ecosystem = "ruby"
package = "edge-fork"
source = "git+https://git.example.org/team/edge-fork.git@0123abcd"
license = "MIT"
note = "LICENSE read at that commit"
```

`init-review-file` writes the `source` line for such rows, from a live scan and with `--from-report`, and adds the `version` line when the scan recorded a version.

Each scaffolded stanza is preceded by `# detected:`, `# status:`, and (when it differs from the detected license) `# raw:` comment lines. Their values are collapsed to a single line and truncated at 200 characters; the full registry string is the `license_raw` field of the JSON report.

Two kinds of flagged dependency get no stanza, from a live scan, with `--from-report`, and with `--merge` alike. Each kind is named on stderr in a `Note: N flagged dependenc(y/ies) could not be scaffolded (<reason>): <names>.` line, and the stanzas of every other dependency are still written:

- A registry dependency with no resolved version (`no resolved version, usually a manifest typo / yanked release / registry miss`): there is no version to key a review on.
- A dependency whose name, version, or source holds a lone surrogate, which is what an unpaired `\uD800`–`\uDFFF` escape in a JSON manifest or report decodes to (`a lone surrogate in the name, version, or source, which a TOML file cannot hold, so no review can be recorded for it`). A TOML string cannot contain one, so no review entry can name such a dependency; it stays flagged. The note shows the surrogate as `\uNNNN`.

When new flagged dependencies appear later, run `licenseal init-review-file --merge` to **add new stanzas** to the existing file. Existing entries are preserved verbatim.

Rules at a glance:

- The match key is the resolved `ecosystem:name@version`. `package` is compared the way the ecosystem's registry compares names: exactly, upper and lower case included, for Go, Java, npm, and Ruby (`example.org/Foo` and `example.org/foo` are two packages, each with its own entry); without regard to case for .NET, PHP, Rust, Hex, and R; with PEP 503 normalization for Python. A Hex dependency that `mix.exs` gives another name than the package it is published as (`{:my_alias, "~> 1.0", hex: :real_pkg}`) is matched on the hex.pm package (`package = "real_pkg"`), so its entry stops matching when the local name is pointed at another package; `init-review-file` writes that name, and the JSON report carries it as `registry_name`. Rows that share a match key (two local names for one hex.pm package at one version) share one entry, and `init-review-file` writes it once.
- An entry with a `source` key matches on ecosystem, package, and `source` instead, compared with the row's `origin` exactly. When it also has a `version`, the row's version must equal it. An entry without `source` never matches an off-registry row, and an entry with `source` never matches a registry row, so two commits of one repository that declare the same version cannot share a review. Messages name such an entry as `off-registry <ecosystem>:<name> from <source>`.
- A review keyed on a commit applies to that commit only. A review keyed on a **branch or a tag** (`git+<url>@main`, which is all a manifest without a lockfile can say) keeps applying when the branch or tag moves to other code, and one keyed on a bare repository URL, a URL without a hash, or a path applies to whatever is there. Pin a commit in the manifest, or commit a lockfile, to get an immutable key. When the origin of a reviewed dependency changes, its entry no longer matches and `check` fails until the new source is reviewed.
- A live `init-review-file` scan (one without `--from-report`) resolves the project exactly as `check` does with its default options: lockfiles first, the transitive graph down to `--max-depth 50`, and the same `--dev` and `--exclude-dirs` handling. It writes a stanza for every row `check` flags, transitive dependencies included, keyed as `check` reports the row: a registry package at its locked version, an off-registry dependency by the origin its lockfile records (the locked commit, not the branch the manifest names). Filling in the stanzas is therefore enough for the next `check` to apply them. A manifest whose dependencies no lockfile covers is named in a `Warning:`, as `check` names it, and its stanzas carry the versions estimated from the registry; the command does not fail for it. For a `check` run with other options (`--no-transitive`, another `--max-depth`), scaffold from that run's report with `--from-report`: a live scan would also write stanzas for rows that run does not report, and a filled-in entry that matches no row fails the command.
- Reviews can only override flagged dependencies, never compatible ones.
- A filled-in entry that matches no reported row, and an invalid entry (a missing or mistyped key, an ecosystem licenseal does not know, a license that is not an SPDX ID or expression, a duplicate), fails the command. An entry whose `license` is empty is not applied: `check` names it in a `Warning:`, and the dependency it is for stays flagged.
- `licenseal.review.toml` and the report passed to `--from-report` must be UTF-8. A file in another encoding (UTF-16 from a Windows shell redirect, for example) ends the command with an error that names the file; write the report with `-o report.json` rather than `>`.
- Reports keep both the detected and reviewed licenses visible; JSON exposes `detected_license`, `reviewed_license`, `effective_license`, `reviewed`, and `review_note`.
- **Strict-mode exit code** skips reviewed entries. A reviewed dep is classified by its reviewed license: one reviewed as a license the project can take counts as `ok`, and one whose reviewed license is still a `warning`, `incompatible`, or `unknown` stays in that bucket (the counter is by classification), but `licenseal check --strict` passes because the review IS the accept-and-document mechanism. Unreviewed warnings / violations / unknowns still fail. **Analysis gaps** are not part of the review mechanism — close them by fixing the file's encoding or syntax, or the path it references; a manifest without a lockfile is closed by committing a lockfile or by passing `--no-require-lockfile`.

Reviewed entries appear in their own report section:

> **Summary:** 0 violations, 0 warnings, 0 unknown, 4 ok (of which 1 reviewed)

| Package | Detected | Reviewed | Note |
| --- | --- | --- | --- |
| mystery-lib (1.0.0) | UNKNOWN (raw: Custom internal license) | MIT | confirmed from packaged LICENSE file |

Because a malicious entry can mark a copyleft dependency as MIT and pass strict mode, treat `licenseal.review.toml` as security-relevant: require code review on every change, document each override's rationale in `note`, and re-validate periodically. (See [SECURITY.md](SECURITY.md).)

## Claude Code skill

licenseal ships a [Claude Code](https://claude.com/claude-code) skill that drives the review workflow interactively — runs `licenseal check`, walks you through each flagged dep, fills in `licenseal.review.toml` from your decisions, and re-verifies that the gaps closed.

```bash
licenseal install-skill                  # <project>/.claude/skills/licenseal-review/SKILL.md
licenseal install-skill --path ../other  # install into another project directory
licenseal install-skill --force          # overwrite a hand-edited skill
```

The skill installs **only inside the project** (`.claude/skills/`), never globally — licenseal never reads or writes outside the project directory, so the skill can be committed alongside the code it audits. Claude Code discovers it automatically; invoke `/licenseal-review` to run it. It consumes the `actionability` block emitted on every flagged dep in the JSON report (`investigate_url` + verdict-aware `next_steps`); the URL trust model is documented in [JSON_OUTPUT.md](JSON_OUTPUT.md).

**Keeping the skill current.** The installed `SKILL.md` is a snapshot, so upgrading the package doesn't update it automatically. When the bundled skill actually changes in a release, the next `licenseal check` prints a one-line reminder, and re-running `install-skill` rewrites an unedited install in place (no `--force` needed). The reminder is content-based (a release that doesn't touch the skill stays quiet), checks only the project-local `.claude/skills`, and is strictly read-only — so it never fires for users who run licenseal without the skill installed. A `SKILL.md` that is not UTF-8 text is treated as hand-edited: `check` ignores it, and `install-skill` replaces it only with `--force`.
